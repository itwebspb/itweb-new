# Design: страница «Техническая поддержка сайта»

Дата: 2026-09-20  
Статус: согласовано в диалоге, ожидает ревью файла

## Цель

Создать элемент услуги «Техническая поддержка сайта» внутри раздела `podderzhka` по существующей дизайн-модели `.dm-page`, адаптировав содержание файла `Техподдержка сайта.html`.

## Структура и доставка

- Bitrix iblock: **21**.
- Родительский раздел: `podderzhka`.
- Элемент: NAME «Техническая поддержка сайта», CODE `tekhnicheskaya`.
- URL: `/services/podderzhka/tekhnicheskaya/`.
- HTML-источник: `bitrix/templates/aspro_max/design-model/pages/uslugi-podderzhka-tekhnicheskaya.html`.
- Контент элемента: `DETAIL_TEXT`, type `html`.
- Manifest: `kind: element`, `section: podderzhka`.
- Meta title: `Техническая поддержка сайта и абонентское обслуживание | Ай Ти Веб`.
- Meta description: `Техническая поддержка и обслуживание сайтов под ключ: обновления, бэкапы, мониторинг 24/7, правки контента, исправление ошибок. От 15 000 ₽ в месяц.`
- После commit и push: remote sync через `scripts/dm-sync-page.sh --env remote --code tekhnicheskaya --css`.

## Визуальный подход

Страница использует компоненты и визуальный язык родительской `/services/podderzhka/`:

- общая обёртка `.dm-page`;
- hero, контейнеры, сетки, карточки, тарифы, кейсы, timeline, tools, FAQ и CTA из `design-model.css`;
- тонкие inline SVG вместо emoji;
- кнопки заявки открывают существующую Aspro-форму `CALLBACK`;
- FAQ реализован нативными `<details>` с schema.org `FAQPage`;
- встроенные `<style>`, JavaScript исходника, самостоятельная HTML-форма и фиктивные контакты не переносятся;
- новый CSS добавляется только при отсутствии подходящего существующего компонента.

## Порядок секций

1. Hero: H1, лид, четыре преимущества, CALLBACK и якорь на тарифы.
2. Что входит в техническую поддержку: стабильность, развитие, скорость/SEO-гигиена.
3. Почему выбирают техподдержку: шесть преимуществ.
4. Тарифы: разовые задачи, «Старт», «Бизнес».
5. Кейсы: три карточки с показателями и корректными ссылками на `/projects/`.
6. Этапы подключения: шесть шагов.
7. Инструменты: восемь карточек.
8. Результаты поддержки: шесть карточек.
9. FAQ: восемь вопросов и ответов.
10. Финальный CTA: текст источника и Aspro CALLBACK без отдельной формы.

## Контентные решения

- Сохраняются смысл, цифры, тарифы, SLA, кейсы и FAQ из загруженного файла.
- Невалидные ссылки `#` заменяются на существующие `/projects/`, callback-кнопки либо удаляются.
- Устаревшие пути `/uslugi/...` не переносятся; внутренняя навигация использует существующие `/services/...`.
- Кнопки и якоря получают уникальные `dm-*` идентификаторы в пределах страницы.
- Родительская страница `podderzhka` не меняется.

## Проверка

До реализации добавляется статическая проверка требований страницы и manifest; она должна сначала упасть из-за отсутствующих артефактов, затем пройти после реализации.

После remote sync проверяются:

- HTTP 200 конечного URL;
- наличие `.dm-page`;
- точный H1 «Техническая поддержка сайта под ключ»;
- подключение и доступность `design-model.css`;
- секции тарифов, кейсов, этапов и CTA;
- schema.org FAQ и ровно восемь FAQ-элементов;
- отсутствие emoji, inline `<style>`, `<script>` и самостоятельной `<form>`;
- совпадение удалённого HTML с HTML-источником commit.

## Вне scope

- Изменение родительской страницы `/services/podderzhka/`.
- Создание отдельных страниц для контентной поддержки и развития.
- Новая серверная форма, телефоны, WhatsApp или Telegram.
- Правки других элементов и разделов iblock 21.

## Критерии готовности

- [ ] Новый HTML-источник использует только согласованные `.dm-*` компоненты.
- [ ] Manifest создаёт `tekhnicheskaya` внутри `podderzhka`.
- [ ] Автоматическая статическая проверка проходит.
- [ ] Изменения committed, pushed и отражены в PR.
- [ ] Страница синхронизирована на staging.
- [ ] Публичный URL проходит все перечисленные проверки.
